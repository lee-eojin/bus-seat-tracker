# 수집기 운영 가이드

수집기는 3330번과 1650번 버스의 위치·잔여석을 GBIS에서 읽어 비공개 저장소에 JSONL로
쌓는다. GitHub Actions의 예약 실행은 수집을 시작하는 신호만 맡고, 1분 단위 관측이 필요한
시간에는 하나의 잡이 창이 끝날 때까지 반복한다. GitHub 예약 실행이 몇 시간 늦어질 수 있다는
실측 때문에 이렇게 나눴다.

운영할 때는 세 가지를 따로 본다.

- **관측 성공**: GBIS에서 두 노선의 스냅샷을 받았는가
- **보관 성공**: 받은 스냅샷이 비공개 저장소의 당일 브랜치에 올라갔는가
- **발행 성공**: 새 스냅샷이 정적 화면과 예측 로그에 반영됐는가

한 단계가 성공해도 다음 단계가 실패할 수 있다. 특히 API 호출 뒤 업로드가 실패하면 쿼터는
이미 썼지만 데이터는 남지 않는다.

## 기준이 되는 파일

| 역할 | 파일 |
|---|---|
| 예약 실행과 새 러너 재시도 | [`.github/workflows/collect-bus-seats.yml`](../../.github/workflows/collect-bus-seats.yml) |
| 수집 한 판 (보관, 브랜치 준비, 수집 루프) | [`.github/workflows/collect-cycle.yml`](../../.github/workflows/collect-cycle.yml) |
| 시간대·간격·운행 시간 판정 | [`tools/collector/src/schedule.ts`](../../tools/collector/src/schedule.ts) |
| GBIS 호출, 노선 캐시, JSONL 저장 | [`tools/collector/src/collector.ts`](../../tools/collector/src/collector.ts) |
| 호출 수 계산 | [`tools/collector/scripts/call-budget.mjs`](../../tools/collector/scripts/call-budget.mjs) |
| 발행 | [`.github/workflows/publish-pages.yml`](../../.github/workflows/publish-pages.yml) |
| 예보 검증 | [`.github/workflows/verify-forecast.yml`](../../.github/workflows/verify-forecast.yml) |

스케줄 표보다 `schedule.ts`가 우선이다. 표를 고친다고 실행 시간이 바뀌지 않는다. 창이나 간격을
바꿀 때는 코드, 경계값 테스트, 호출 예산을 함께 확인한다.

## 데이터와 비밀정보의 경계

```text
공개 bus-seat-tracker
  ├─ 수집·집계 코드
  ├─ 차량 ID를 제거한 정적 집계
  └─ 차량 번호와 ID를 제거한 /api/live 응답

비공개 bus-seat-tracker-data
  ├─ data/routes/*.json
  ├─ data/snapshots/*.jsonl
  └─ predictions/*.jsonl   # predictions 브랜치
```

수집 원문에는 HMAC으로 가명화한 차량 ID가 들어간다. 이름을 바로 알 수 없는 값이어도 날짜를
넘어 같은 차량을 이을 수 있으므로 공개 데이터로 취급하지 않는다. 공개 번들을 만들 때는 가명
ID도 `null`로 지운다. 라이브 예측 원문도 같은 가명 ID를 쓰기 때문에 `predictions` 브랜치 밖으로
내보내지 않는다.

### GitHub Actions Secrets

| 이름 | 용도 | 관리 원칙 |
|---|---|---|
| `GYEONGGI_BUS_API_KEY` | GBIS 노선·위치 조회 | 포털 키 원문을 로그나 문서에 남기지 않는다 |
| `VEHICLE_HASH_SECRET` | 차량 번호·ID의 HMAC 키 | API 키와 다른 긴 임의값을 쓴다 |
| `BUS_DATA_REPO_TOKEN` | 비공개 데이터 저장소 읽기·쓰기 | 해당 저장소의 Contents 권한만 준다 |

`VEHICLE_HASH_SECRET`은 평상시 API 키 교체와 함께 바꾸지 않는다. 이 값이 바뀌면 같은 차량의
가명 ID가 전후 기간에 이어지지 않아 운행 추적과 라이브 예측 채점이 끊긴다. 유출이 의심되면
연결 단절을 감수하고 교체한 뒤, 변경 시각을 연구 기록에 남긴다.

`BUS_DATA_REPO_TOKEN`은 **Collect bus seats**, **Publish seat board**, **Verify forecast**가 함께
쓴다. 토큰 교체 순서와 Vercel의 읽기 전용 토큰 분리는 [배포 운영 가이드](deployment.md#토큰-교체-절차)를
따른다.

## 로컬에서 한 번 수집하기

Node.js 22가 필요하다. `.env`는 `tools/collector/` 안에서만 읽으며 공개 저장소에 포함하지 않는다.

```bash
npm ci
cp tools/collector/.env.example tools/collector/.env
```

`.env`에는 실제 값을 직접 입력한다.

```dotenv
GYEONGGI_BUS_API_KEY=<경기도 버스정보 API 일반 인증키>
VEHICLE_HASH_SECRET=<API 키와 다른 긴 임의값>
ROUTE_NAMES=3330,1650
```

한 번만 수집해 경로와 응답을 확인한다.

```bash
npm run collect -- --once
```

노선 개수, 운행 차량 수와 함께 저장 완료 로그가 나와야 한다. 기본 저장 위치는 저장소 루트의
`data/`이고, Actions에서는 `BUS_DATA_DIR`로 비공개 저장소의 `data/`를 지정한다.

노선이 실제로 개편됐거나 캐시가 잘못됐다고 확인했을 때만 강제로 갱신한다.

```bash
npm run collect -- --once --refresh-routes
```

노선 정보 갱신이 실패해도 기존 캐시가 있으면 그 캐시로 위치 수집을 계속한다. 캐시가 하나도
없는 노선만 이번 사이클에서 빠지며, 모든 노선이 빠질 때 실행이 실패한다. 강제 갱신은 문제를
확인한 뒤 사용한다. 불필요한 갱신은 `busrouteservice` 쿼터를 쓴다.

## 자동 수집 시간표

모든 시각은 KST다. 아래 표는 `schedule.ts`의 현재 상수를 풀어 썼다.

| 요일·시간 | 간격 | 실행 방식 |
|---|---:|---|
| 평일 05:00~06:29 | 매시 1회 | 정시 예약 실행이 단발 수집 |
| 평일 06:30~07:00 | 10분 | 아침 창 루프 |
| 평일 07:00~09:00 | 1분 | 아침 조밀 구간 |
| 평일 09:00~10:00 | 10분 | 아침 창 루프 |
| 평일 10:00~16:00 | 20분 | 낮 창 루프 |
| 수요일 13:00~13:30 | 2분 | 낮 역산 보정 구간 |
| 평일 16:00~17:29 | 매시 1회 | 정시 예약 실행이 단발 수집 |
| 평일 17:30~18:00 | 10분 | 저녁 창 루프 |
| 평일 18:00~19:30 | 1분 | 저녁 조밀 구간 |
| 평일 19:30~20:30 | 10분 | 저녁 창 루프 |
| 평일 20:30~21:59 | 매시 1회 | 정시 예약 실행이 단발 수집 |
| 주말 06:00~23:59 | 매시 1회 | 정시 예약 실행이 단발 수집 |
| 그 밖의 심야 | 수집 없음 | 보관 단계만 거친 뒤 수집 단계에서 종료 |

아침·낮·저녁 창은 시작 60분 전부터 잡을 인수할 수 있다. 전용 시동이 늦거나 빠져도 매시 실행이
남은 창을 이어받기 위한 장치다. 창 시작 전에 인수한 실행은 즉시 한 번 수집한 뒤 시작 시각까지
기다린다. 이 추가 사이클도 호출 예산 계산에 들어간다.

워크플로는 아래 세 예약식으로 시작한다.

| UTC cron | KST 역할 |
|---|---|
| `0 * * * *` | 매시 정시 단발 수집과 백업 시동 |
| `30 21 * * 0-4` | 월~금 06:30 아침 창 시동 |
| `30 8 * * 1-5` | 월~금 17:30 저녁 창 시동 |

동시에 두 수집 잡을 돌리지 않는다. `bus-seat-collection` 동시성 그룹이 실행 중인 잡을 유지하고
다음 실행을 대기시킨다. 하나의 잡은 최대 320분까지만 루프를 돌고, 워크플로 자체 제한은
350분이다. 남은 창은 대기 중인 실행이 이어받는다.

## 한 사이클에서 일어나는 일

1. 24시간 안에 받은 노선·정류장 캐시가 있으면 재사용한다.
2. 3330과 1650의 차량 위치를 병렬로 조회한다.
3. `plateNo` 또는 `vehId`를 `VEHICLE_HASH_SECRET`으로 HMAC 처리해 앞 16자리만 남긴다.
4. `data/snapshots/<노선>-<KST 날짜>.jsonl`에 한 줄을 덧붙인다.
5. Actions가 바뀐 파일만 비공개 저장소의 당일 브랜치에 올린다.

한 노선이 실패해도 성공한 노선의 파일은 먼저 저장하고 업로드한다. 그 뒤 사이클을 실패로 돌려
워크플로의 재시도 정책이 작동하게 한다. 두 노선 중 하나만 계속 비는 장애를 전체 실패와 같은
방법으로 덮어쓰지 않기 위한 처리다.

### 실패와 재시도

| 실패 | 동작 |
|---|---|
| 데이터 저장소 401·403 | 첫 실패에서 루프 중단, 잡 실패 |
| 그 밖의 사이클 오류 | 연속 3회에서 루프 중단, 성격에 따라 잡 실패 또는 경고 |
| 창 밖 단발 수집 오류 | 45초 간격으로 최대 3회 재시도 |
| 실패 사이클 안의 일부 노선 성공 | 성공 파일을 먼저 업로드한 뒤 실패 처리 |
| 저절로 낫는 실패로 한 건도 못 건짐 | 새 러너에서 한 판 더 (`retry-on-fresh-runner`) |
| GitHub API 429·5xx | 보관·브랜치 준비 단계에서 최대 5회, 15·30·45·60초 간격 재시도 |

인증 실패를 오래 재시도하지 않는 이유는 호출 순서 때문이다. GBIS를 먼저 호출하고 그다음 파일을
올리므로, 저장소 토큰이 죽은 상태에서 반복하면 좌석 API 쿼터만 사라진다.

### 실패의 성격 구분

같은 빨간불이라도 사람이 할 수 있는 일이 있는 실패와 없는 실패는 다르다. 판단 규칙은
[`tools/collector/src/failure-kind.ts`](../../tools/collector/src/failure-kind.ts)에 있고,
수집기가 종료 코드로 알린다. 저절로 낫는 실패면 10, 그 밖에는 1이다.

| 성격 | 예 | 실행 결과 |
|---|---|---|
| 저절로 낫는다 | 연결 타임아웃(`UND_ERR_CONNECT_TIMEOUT`), 소켓 끊김, 상류 5xx와 429, 요청 예산 초과 | 경고와 실행 요약. 새 러너에서 한 판 더 |
| 사람이 손대야 한다 | 서비스키 미등록과 기한만료, 호출 한도 소진, 401과 403, 데이터 저장소 토큰 만료 | 잡 실패 |

분류는 화이트리스트다. 자가 치유가 확실한 갈래만 경고로 내리고 모르는 실패는 전부 잡 실패로
남긴다. 반대로 두면 키가 죽은 날 아무도 모른다.

원인은 `error.cause` 체인을 끝까지 펼쳐 한 줄로 남긴다. 예전에는 메시지만 읽어서
`TypeError: fetch failed`에서 끊겼고, 알림에는 `Command failed: node .../collector.js --once`만
떴다. 지금은 이렇게 나온다.

```
수집기를 시작하지 못했습니다 [transient]: 수집할 노선을 하나도 확인하지 못했습니다: 3330, 1650번
  ← 상류에 연결하지 못했습니다 (/busrouteservice/v2/getBusRouteListv2)
  ← The operation was aborted due to timeout
```

상류가 HTTP 200 본문에 오류를 담아 보내는 경우도 검사한다. 이걸 보지 않으면 항목 목록이 비어
"운행 차량 0대 저장"으로 성공 집계되고 빈 스냅샷이 정상 관측으로 남는다. 운행 차량이 없다는
응답(`NODATA`, 사유 코드 03)은 오류가 아니라 정상이다.

### 새 러너 재시도

GBIS 연결 실패는 상류가 아니라 러너의 송신 경로 문제다. 2026-08-07 11:21:11Z에 한 러너가 51대를
정상 수신하는 동안 같은 순간 다른 러너는 두 노선 모두 연결에 실패했다. 첫 사이클에 연결된 러너의
이후 실패율은 0.11%인데 첫 사이클 실패율은 11%다. 한번 막힌 러너는 끝까지 막혀 있어서, 같은
잡 안에서 더 재시도해도 소용이 없다.

그래서 수집 한 판을 [`collect-cycle.yml`](../../.github/workflows/collect-cycle.yml)로 떼고,
저절로 낫는 실패로 한 건도 못 건지면 별도 잡에서 한 번 더 부른다. 별도 잡이라야 새 러너가
배정된다. 재시도는 한 번뿐이고, 두 번째도 실패하면 경고만 남는다. 그 시점엔 사람이 할 수 있는
일이 없기 때문이다.

### 요청 타임아웃

성공 사이클은 두 노선을 합쳐 0.9\~1.6초에 끝난다. 요청 예산은 6초이고 `GBIS_REQUEST_TIMEOUT_MS`로
바꾼다. 예전 15초는 undici의 기본 연결 타임아웃(10초)에 밀려 연결 단계에서 발화조차 못 하던
죽은 예산이었다.

## 일별 브랜치와 보관

수집일은 KST로 계산한다. 당일 데이터는 `collect/YYYY-MM-DD` 브랜치에 사이클별로 쌓고, 다음
날 처음 시작한 수집 잡이 전날 브랜치를 `main`에 날짜당 한 커밋으로 옮긴 뒤 브랜치를 지운다.

보관 판단과 브랜치 준비 판단은 [`tools/collector/src/branch-archive.ts`](../../tools/collector/src/branch-archive.ts)
한 곳에 있고 워크플로가 그것을 불러 쓴다. 규칙이 YAML 안에 있으면 경계를 시험할 수 없어서
분리했다. 상태별 동작은 이렇다.

| `main`과 브랜치 비교 | 보관 | 오늘 브랜치 준비 |
|---|---|---|
| 브랜치가 앞섬 | 브랜치 트리를 그대로 올리고 브랜치 삭제 | 그대로 쓴다 |
| 내용 같음 | 올릴 것 없이 브랜치만 삭제 | 그대로 쓴다 |
| 브랜치가 뒤처짐 | 새 데이터가 없으므로 브랜치만 삭제 | 지우고 다시 만든다 |
| 갈라짐 | 두 트리를 합쳐서 올리고 브랜치 삭제 | 그대로 두고 보관에서 합친다 |

갈라진 브랜치를 예전에는 오류로 던져 사람을 기다렸다. 보관이 수집보다 앞 단계라 그동안
수집이 통째로 멈췄고, 실제로 19시간이 날아갔다
([2026-08-08 기록](incidents/2026-08-08-collection-branch-divergence.md)). 지금은 `main` 트리를
바닥에 깔고 브랜치 파일을 덮어 양쪽을 모두 남긴다. 이 저장소의 데이터 파일은 날짜별로 추가만
되고 지워지지 않으므로 합집합이 언제나 정답이다. 끝난 날짜 브랜치가 여럿이면 날짜 순으로
따라잡는다.

보관 단계는 `continue-on-error`라 실패해도 수집을 막지 않는다. 대신 경고가 실행 요약에 남으므로
같은 경고가 며칠 이어지면 사람이 본다.

## 가동과 일상 점검

### 처음 켤 때

1. 세 Actions Secret의 이름과 저장소 권한을 확인한다.
2. Actions에서 **Collect bus seats**를 수동 실행한다.
3. 로그에서 `2개 노선` 저장과 당일 `collect/YYYY-MM-DD` 브랜치 업로드를 확인한다.
4. 비공개 저장소의 `data/snapshots/3330-YYYY-MM-DD.jsonl`과
   `1650-YYYY-MM-DD.jsonl` 마지막 줄에서 `collectedAt`이 실행 시각과 맞는지 본다.
5. 원문 `plateNo`·`vehId`가 저장되지 않았고 차량 `id`가 16자리 가명값인지 확인한다.
6. **Publish seat board**를 실행하고 공개 `latest.js`에는 차량 `id`가 남지 않았는지 확인한다.

### 매일 볼 것

- 최근 **Collect bus seats**의 결론과 실패 단계
- 현재 시간대의 기대 간격에 맞는 두 노선의 마지막 `collectedAt`
- 당일 `collect/YYYY-MM-DD` 브랜치가 존재하고 파일이 계속 커지는지
- 끝난 날짜 브랜치가 쌓여 있지 않은지. 이제 자동으로 따라잡지만 며칠 남아 있으면 보관 단계가
  계속 실패하고 있다는 뜻이다
- **Publish seat board** 이후 공개 `latest.js`의 `generatedAt`과 `collectedAt`
- **Verify forecast**의 수집 공백 경고
- 공공데이터포털의 실제 일 사용량과 `npm run budget`의 이론값 차이

심야의 예약 실행이 성공하면서 스냅샷이 생기지 않은 것은 정상이다. 로그의 `심야 휴지`를 확인한다.
반대로 운행 시간인데 초록색 실행만 있고 파일 시각이 늘지 않았다면 업로드와 노선별 로그를 함께
본다.

## 호출 예산

`buslocationservice`의 코드상 일 한도는 1,000회다. 수집과 `/api/live`가 같은 한도를 나눠 쓴다.
숫자를 손으로 고정하지 않고 스케줄 정의로 계산한다.

```bash
npm run budget
npm run budget -- --detail
```

현재 상수로 계산한 이론 최대치는 아래와 같다.

| 요일 | 수집 사이클 | 수집 호출 | `/api/live` | 합계 | 여유 |
|---|---:|---:|---:|---:|---:|
| 월·화·목·금 | 253 | 506 | 390 | 896 | 104 |
| 수 | 267 | 534 | 390 | 924 | 76 |
| 토·일 | 18 | 36 | 390 | 426 | 574 |

계산기가 전제로 두는 값은 2개 노선, 실시간 노출 6.5시간, CDN 캐시 120초다. `routeCount`와
`liveExposureHours`는 `call-budget.mjs`의 상수이므로 노선을 추가하거나 노출 시간을 바꾸면 함께
고쳐야 한다. 실제 포털 한도가 1,000회와 같은지도 마이페이지에서 확인한다.

표에는 다음 호출이 들어가지 않는다.

- 실패 뒤 재시도한 위치 조회
- 수동 이벤트 수집
- 노선 캐시 갱신에 쓰는 별도 `busrouteservice` 호출

남은 JSONL 줄 수로 API 사용량을 역산하지 않는다. 업로드 실패 전의 GBIS 호출은 파일에 남지
않는다. 포털 사용량이 예산보다 많다면 재시도, 수동 실행, 캐시 미적중부터 찾는다.

### 수동 이벤트 수집

콘서트나 경기처럼 평소 시간표보다 촘촘히 볼 날에는 **Collect bus seats**의 **Run workflow**에서
두 값을 넣는다.

| 입력 | 뜻 | 기본값 |
|---|---|---:|
| `event-duration-minutes` | 시간대 규칙을 무시하고 반복할 시간 | 비우면 일반 시간표 |
| `event-interval-seconds` | 이벤트 반복 간격 | 300초 |

실행 전에 추가 호출을 계산한다.

```text
추가 위치 호출 ≈ ceil(수집 시간(분) × 60 ÷ 간격(초)) × 노선 수
```

예를 들어 240분을 300초 간격으로 두 노선 수집하면 약 96회를 더 쓴다.

```text
ceil(240 × 60 ÷ 300) × 2 = 96회
```

월요일 이론값 896회에 더하면 992회지만, 수요일 924회에 더하면 1,020회로 한도를 넘는다.
동시성 대기 때문에 일부 정규 실행이 밀릴 수 있어도 그것을 절감분으로 잡지 않는다. 재시도 여유도
필요하므로 합계가 1,000회 바로 아래라는 이유만으로 안전하다고 판단하지 않는다. 포털의 당일 실제
사용량을 확인하고, 한도를 넘거나 남은 양을 확인할 수 없으면 더 긴 간격이나 짧은 시간을 택한다.

## 장애 대응

| 로그·증상 | 조치 |
|---|---|
| `Bad Credentials`, 401, 403 | `BUS_DATA_REPO_TOKEN`의 만료·권한을 확인하고 세 Actions 워크플로를 다시 검증한다 |
| GBIS가 JSON 대신 오류문을 반환 | API 키 상태와 포털 사용량을 확인한다. 응답 원문을 공개 채널에 붙이지 않는다 |
| 한 노선만 반복 실패 | 성공 노선 파일은 보존한다. 실패 노선의 route ID, 캐시, GBIS 응답 상태를 따로 본다 |
| `승차 불가 지점을 찾지 못했습니다` | GBIS 정류장 이름 표기가 바뀌었는지 확인하고 `nonBoardingMarkers`를 검토한다 |
| 단발 수집 전체 실패 | 그 시간대 관측은 복구할 수 없다. 원인을 고친 뒤 현재 시점에서 다시 수집한다 |
| 끝난 수집 브랜치가 여러 개 | 각 브랜치의 날짜·파일·마지막 관측을 확인한 뒤 수동 보관 계획을 세운다 |
| 화면만 오래됨 | 수집 파일이 최신이면 [배포 운영 가이드](deployment.md#증상별-확인-순서)의 발행 경로를 본다 |
| 수집 공백 경고 | [`forecast-validation.md`](forecast-validation.md#수집-공백과-발행-신선도)를 따라 실제 공백과 오탐을 구분한다 |

이미 놓친 관측은 다시 만들 수 없다. 장애가 끝난 뒤 과거 시각의 스냅샷을 합성해 채우지 않는다.
백테스트와 프로파일이 가짜 연속 관측으로 오염되기 때문이다.

2026-07-27의 토큰 장애와 그 뒤 추가한 중단 정책은
[장애 기록](incidents/2026-07-27-token-expiry.md)에 정리했다.
