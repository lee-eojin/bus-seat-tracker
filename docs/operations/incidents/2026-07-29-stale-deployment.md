# 2026-07-29 Vercel 정적 데이터 지연

- 발견일: 2026-07-29
- 관측된 최대 지연: 13.6시간
- 상태: 사건 기록. 현재 설정은 아래 확인 절차로 별도 검증 필요
- 영향 범위: Vercel 정적 스냅샷과 프로파일

## 요약

Vercel의 정적 데이터가 13.6시간 동안 갱신되지 않았다. `/api/live`는 요청 시 GBIS를 조회하는
별도 함수라 실시간 좌석은 계속 보였지만, 화면에 함께 들어가는 최신 스냅샷과 과거 프로파일은
이전 배포 시점에 머물렀다. 화면의 신선도 배너가 수집 중단 상태를 표시했다.

원인은 Vercel Git 연동을 데이터 갱신 경로로 잘못 본 데 있었다. Git 연동은 공개 코드 저장소의
변경으로 배포를 시작한다. 수집 데이터는 별도 비공개 저장소에서 바뀌므로 코드 변경이 없는 날에는
Vercel 배포가 시작되지 않는다. `VERCEL_DEPLOY_HOOK_URL`이 없으면 이 간극을 메울 방법이 없었다.

## 영향

- Vercel 화면의 `latest.js`, `history.js`, `profile.js`가 최대 13.6시간 오래된 상태였다.
- 실시간 좌석과 정적 예보 재료의 시점이 서로 달라졌다.
- 화면은 실시간 차량 위치를 보여 주면서도 프로파일과 스냅샷 기반 판정에는 오래된 데이터를
  사용할 수 있었다.
- GitHub Pages 발행과 예측 로그 적재가 정상이어도 Vercel만 뒤처질 수 있는 구조가 드러났다.

원본 수집 데이터 손실이나 비밀정보 노출은 이 사건의 영향으로 확인되지 않았다.

## 발견과 원인 분석

배포 주소의 신선도 배너와 정적 번들의 시각을 확인해 지연을 발견했다. 실시간 함수가 살아 있어
서비스 전체 장애로 보이지 않았고, Vercel의 마지막 성공 배포도 실패 상태가 아니었다.

직접 원인은 정적 데이터 갱신을 시작할 Deploy Hook의 부재였다. 아래 조건도 발견을 늦췄다.

1. “Git 연결이 있으면 Hook은 중복”이라고 판단했다.
2. 데이터 저장소 변경은 공개 코드 저장소의 커밋을 만들지 않는다는 점을 배포 절차에서 분리하지
   않았다.
3. `Publish seat board`는 Hook Secret이 없을 때 경고 후 성공으로 끝나므로, 워크플로 상태만 보면
   발행 누락을 알 수 없었다.
4. 정적 번들의 `generatedAt`과 노선별 `collectedAt`을 외부에서 감시하는 장치가 없었다.

## 대응

발행 워크플로에 Vercel Deploy Hook 호출 경로를 두고, 비공개 데이터로 정적 번들을 다시 만들 수
있게 했다. 현재 코드에서 **Publish seat board**는 매시 17분과 47분에 다음 작업을 수행한다.

1. 당일 수집 브랜치가 있으면 그 데이터를 읽는다.
2. 화면용 데이터와 라이브 예측 로그를 만든다.
3. GitHub Pages에 `site/`를 배포한다.
4. `VERCEL_DEPLOY_HOOK_URL`이 있으면 Vercel 재배포를 요청한다.

Hook이 없을 때 발행 전체를 실패시키지는 않는다. 예측 로그와 Pages까지 함께 멈추는 피해를 피하기
위해서다. 대신 로그에 경고를 남긴다. 이 선택 때문에 초록색 워크플로만으로 Vercel 갱신을
증명할 수 없다는 점은 그대로 남는다.

## 재발 여부 확인

외부 설정인 Secret과 Deploy Hook의 현재 상태를 문서에 고정하지 않는다. 아래 순서로 끝까지
확인한다.

1. Actions에서 **Publish seat board**를 수동 실행한다.
2. `Trigger Vercel deploy` 단계에 `VERCEL_DEPLOY_HOOK_URL 미설정` 경고가 없는지 본다.
3. 그 실행 뒤 Vercel에 새 배포가 시작됐는지 대시보드에서 확인한다.
4. 빌드 로그가 당일 `collect/YYYY-MM-DD` 또는 `main` 중 어느 데이터를 읽었는지 확인한다.
5. 공개 `/data/latest.js`의 `generatedAt`과 노선별 `collectedAt`을 읽는다.
6. 같은 실행에서 배포한 GitHub Pages 값과 Vercel 값을 비교한다.

확인 명령은 [배포 운영 가이드의 배포 확인 절차](../deployment.md#배포-확인)에 있다.

## 다시 발생했을 때

| 관측 | 판단과 조치 |
|---|---|
| Pages와 Vercel이 모두 오래됨 | 수집과 Publish 워크플로를 먼저 확인한다 |
| Pages는 최신이고 Vercel만 오래됨 | Hook Secret, Hook 응답, Vercel 배포 목록을 확인한다 |
| `generatedAt`은 최신인데 `collectedAt`이 오래됨 | 배포가 아니라 수집 공백이다 |
| `/api/live`만 정상 | 정적 데이터 경로가 멈췄을 가능성이 높다 |
| Vercel 빌드가 데이터 저장소 인증으로 실패 | Vercel 읽기 전용 `BUS_DATA_REPO_TOKEN`을 확인한다 |

원인을 고친 뒤 **Publish seat board**를 다시 실행하고, Vercel 배포 완료와 `latest.js` 시각까지
확인한다. 단순히 Deploy Hook 요청이 2xx였다는 사실만으로 복구를 선언하지 않는다.

## 남은 위험

- Hook Secret이 없어도 `Publish seat board`는 성공 결론을 낼 수 있다.
- Deploy Hook 호출 성공은 빌드와 실제 공개 반영 성공을 보장하지 않는다.
- 저장소에는 외부 공개 주소의 `generatedAt`을 주기적으로 검사하는 모니터가 없다.
- Pages와 Vercel을 함께 운영하는 동안 두 배포본이 서로 다른 시점일 수 있다.

운영 점검에서는 워크플로 결론, Vercel 배포, 공개 번들의 시각을 한 묶음으로 본다. 외부 신선도
모니터를 추가하기 전까지는 이 세 단계 확인이 재발 방지의 마지막 장치다.
