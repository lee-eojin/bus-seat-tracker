# 2026-07-27 데이터 저장소 토큰 만료

- 발생 구간: 2026-07-27 18:40~21:16 KST
- 영향 시간: 2시간 36분
- 상태: 당시 복구 완료
- 영향 범위: 저녁 수집과 정적 화면 발행

## 요약

Vercel 빌드에 넣을 Personal Access Token(PAT)을 다시 발급하는 과정에서 GitHub Actions가 쓰던
기존 `BUS_DATA_REPO_TOKEN`이 무효화됐다. **Collect bus seats**는 `401 Bad Credentials`,
**Publish seat board**는 종료 코드 128로 실패했다. GitHub Secret을 새 값으로 바꾸고 두
워크플로를 수동 실행해 21:16에 다시 가동했다.

중단된 저녁 피크 관측은 복구할 수 없었다. 더 큰 문제는 당시 수집 루프가 저장소 업로드 실패를
경고로만 남기고 계속 돌았다는 점이다. 51사이클 동안 두 노선 위치 API를 호출해 102회를 썼지만
스냅샷은 한 건도 남지 않았다.

## 영향

- 18:40부터 21:16까지 새 스냅샷이 비공개 저장소에 쌓이지 않았다.
- 같은 토큰을 쓰던 정적 화면 발행도 멈췄다.
- 저녁 피크 끝자락의 관측 공백이 생겼고 사후 백필은 불가능했다.
- `buslocationservice` 호출 102회가 데이터 없이 소비됐다.
- 업로드 오류가 경고에 머물러 수집 루프가 창 끝까지 계속됐다.

개인정보나 토큰 값이 공개된 정황은 기록에 없다. 이 사건은 토큰 유출이 아니라 교체 과정에서
기존 자격 증명이 먼저 무효화된 가용성 장애였다.

## 시간순 기록

| 시각(KST) | 확인된 일 |
|---|---|
| 18:40 | 수집과 발행 중단 시작 |
| 중단 중 | Collect에서 401, Publish에서 종료 코드 128 발생 |
| 중단 중 | 수집 루프가 51사이클을 계속 실행해 위치 조회 102회 소비 |
| 21:16 | GitHub Secret 교체 후 수집과 발행 수동 실행으로 복구 |

PAT를 재발급한 정확한 시각과 최초 탐지 시각은 남은 기록만으로 분리할 수 없다. 추정 시각을
사실처럼 채우지 않는다.

## 원인

Vercel용 토큰을 준비하면서 기존 PAT를 재발급했고, Actions Secret에 남아 있던 값이 즉시
무효화됐다.

피해를 키운 조건은 세 가지였다.

1. Vercel 빌드와 Actions 자동화의 권한 차이를 구분하지 않고 토큰 교체를 진행했다.
2. 같은 `BUS_DATA_REPO_TOKEN`을 쓰는 수집과 발행 소비자를 교체 전에 목록으로 확인하지 않았다.
3. 수집기는 GBIS 호출 뒤 업로드에 실패해도 `warning`만 남기고 다음 사이클을 실행했다.

## 복구

1. GitHub Actions의 `BUS_DATA_REPO_TOKEN`을 유효한 값으로 교체했다.
2. **Collect bus seats**를 수동 실행해 당일 스냅샷 쓰기를 확인했다.
3. **Publish seat board**를 수동 실행해 정적 발행을 다시 시작했다.

놓친 시간대의 원본 관측은 만들지 않았다. 과거 시각을 붙인 합성 스냅샷은 모델 학습과 검증을
오염시키므로 공백으로 보존하는 편이 맞다.

## 재발 방지

현재 워크플로 코드에는 다음 방어가 들어 있다.

- 데이터 저장소 업로드에서 401이나 403이 나오면 첫 실패에 루프를 중단한다.
- 인증 외 오류도 연속 3회면 중단한다.
- 중단할 때 `core.setFailed`로 잡을 실패 처리한다.
- 한 노선이 성공했다면 실패를 보고하기 전에 성공 파일부터 업로드한다.
- 창 밖 단발 수집은 45초 간격으로 3분 안에서만 재시도한다.

토큰 운영 절차도 분리했다.

- Vercel에는 비공개 데이터 저장소 **읽기 전용** 토큰을 쓴다.
- GitHub Actions에는 해당 저장소 Contents **읽기와 쓰기** 토큰을 쓴다.
- 평상시 교체는 새 토큰으로 모든 소비자를 검증한 뒤 옛 토큰을 폐기한다.
- 유출 대응은 옛 토큰을 먼저 폐기하되, 중단을 예상하고 세 워크플로를 차례로 복구한다.

자세한 순서는 [배포 운영 가이드의 토큰 교체 절차](../deployment.md#토큰-교체-절차)를 따른다.

## 현재 방어가 작동하는지 확인하는 법

저장소 코드만으로 GitHub Secret의 현재 값이나 만료일을 알 수 없다. 다음 증거를 직접 확인한다.

1. **Collect bus seats** 수동 실행에서 당일 브랜치의 JSONL 시각이 늘어난다.
2. **Publish seat board**가 비공개 저장소를 읽고 `predictions` 브랜치에 쓸 수 있다.
3. **Verify forecast**가 데이터를 읽고 오래된 예측 파일을 정리할 수 있다.
4. 인증 실패를 재현할 필요가 있다면 실제 운영 키를 망가뜨리지 말고 별도 테스트 저장소와
   제한된 임시 토큰을 사용한다.
5. 실패 로그에 토큰 원문이나 인증 URL이 출력되지 않았는지 확인한다.

## 남은 위험

- 토큰 만료일 자체를 이 저장소가 감시하지 않는다.
- GitHub Secret 하나가 세 워크플로의 데이터 접근을 함께 담당한다.
- 실패 전 이미 실행된 GBIS 호출은 되돌릴 수 없다.

만료 알림은 토큰 발급처에서 따로 관리한다. 장애를 판단할 때도 워크플로 성공 여부와 실제
JSONL의 마지막 `collectedAt`을 함께 확인해야 한다.
