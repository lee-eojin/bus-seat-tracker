# 탑승 지점 추천 모델 v2 설계

상태: 설계안, 부분 구현 (2026-08-05 재정리)

이 문서는 현재 좌석 예보를 개인의 탑승 지점 추천으로 확장하는 방향을 설명한다. 지금 배포된 코드와 목표 설계를 섞지 않기 위해, 구현 여부를 먼저 밝힌다.

| 구성 | 상태 | 현재 문서 |
|---|---|---|
| 구간합 역산과 도착 좌석 분포 | 구현됨 | [좌석 예보](../model/seat-forecast.md) |
| `여유`, `빠듯`, `어려움` 규칙 | 구현됨 | [탑승 판정](../model/boarding-verdict.md) |

원래 v2 명세는 [보관 문서](../archive/boarding-model-v2-original-2026-07-21.md)에 그대로 남겼다. 이 문서는 그 설계에서 여전히 유효한 결정만 추려 현재 구현과 연결한 버전이다.

## 1. 왜 좌석 예보만으로 부족한가

버스가 정류장에 5석을 남기고 도착한다고 하자. 앞에 2명이 있으면 탈 수 있지만 앞에 8명이 있으면 못 탄다. 반대로 대기자가 많아도 그 정류장에서 사람이 많이 내리면 탈 수 있다.

개인 탑승 결과에는 적어도 세 종류의 불확실성이 함께 들어간다.

1. 버스가 도착할 때 실제로 몇 석이 남는가.
2. 사용자가 줄에 들어갔을 때 앞에 몇 명이 있는가.
3. 사용자가 후보 정류장에 버스보다 먼저 도착하는가.

현재 제품은 첫 번째를 모델로 계산하고, 두 번째는 시간대 수요와 만석 연속 횟수로 보수적으로 대신한다. 별도의 과거 만석 빈도 규칙이 상류 정류장을 고르기도 하지만 세 번째는 계산하지 않는다. 그래서 화면이 상류 이동을 권해도 사용자가 버스보다 먼저 도착할지는 검증하지 않은 상태다.

## 2. 노선 좌석 상태를 더 정확히 추정하기

### 현재 방식

현재 구현은 구간의 시작이나 끝 잔여석이 0인 관측쌍을 수치 학습에서 제외하고, 나머지 구간합으로 정류장별 평균과 분산을 역산한다. 차량별 실제 정원을 알지 못하므로 정원 상한에 닿은 관측은 별도 검열로 다루지 않는다. 계산이 빠르고 단순 기준선보다 나았지만, 만석 초과 수요와 정원 쪽 검열을 충분히 배우지 못한다.

### 목표 방식

목표는 실제 순수요를 숨은 상태로 두고, 관측이 주는 정보의 종류에 맞춰 우도를 다르게 쓰는 것이다.

```text
0 < S⁺ < C  →  순수요를 등식으로 관측
S⁺ = 0      →  순수요의 하한만 관측
S⁺ = C      →  순수요의 상한만 관측
```

여러 정류장을 건너뛴 관측은 중간 경로 전체가 시작 좌석과 끝 좌석을 연결해야 한다는 제약으로 사용한다. 중간에 만석이 됐다가 하차로 회복하는 경로도 허용해야 한다. 실제 관측에서 `양수 → 0 → 양수` 전이가 확인됐기 때문이다.

정류장 `k`, 시간대 `b`, 평일과 주말 구분 `g`의 평소 순수요를 `μ_kbg`라고 두고, 날짜별 혼잡 효과와 배차 간격을 더한다.

```text
N = μ_kbg + a_k × u_day + βᵀx_day + γ × log(headway) + v_run + ε
```

- `u_day`: 이유를 전부 설명하지 못해도 그날 전체가 평소보다 붐비는 정도
- `a_k`: 같은 혼잡 효과에 정류장마다 다르게 반응하는 정도
- `x_day`: 비, 공휴일처럼 관측 가능한 날짜 조건
- `headway`: 앞차와의 실제 간격
- `v_run`: 특정 운행에만 생긴 차이

비율 배수 하나를 곱하지 않는 이유는 순수요가 음수가 될 수 있기 때문이다. 승차가 많은 정류장과 하차가 많은 정류장이 섞인 합은 0 근처에서 쉽게 흔들린다.

## 3. 사용자 앞 경쟁 수요를 따로 모델링하기

좌석 흐름이 알려 주는 값은 정류장 전체의 `탑승 - 하차`다. 개인에게 필요한 값은 사용자가 줄에 들어선 순간 앞에 있던 사람과, 버스에서 내릴 사람의 차이다. 둘은 같은 변수가 아니다.

사용자 앞 대기자를 `Q`, 해당 정류장 하차를 `A`라고 두면 경쟁 수요는 다음과 같다.

```text
H = Q - A
```

도착 직전 좌석이 `S⁻`일 때, 선착순 승차가 지켜진다는 조건에서 사용자가 탈 수 있는 가장 단순한 조건은 `S⁻ > H`다.

이 값을 학습하려면 좌석 API만으로는 부족하다. 적어도 다음 기록이 필요하다.

```text
사용자가 줄에 선 시각
버스가 도착한 시각
사용자 앞 대기자 수
하차 인원
실제 탑승 여부
줄 순서가 깨졌는지 여부
추천받은 행동과 실제 선택
```

기준 정류장 자료만으로 상류 후보의 개인 성공 확률을 만들지 않는다. 인접 정류장 자료는 초기 사전분포를 돕지만 직접 관측을 대체할 수 없다.

자료가 부족한 후보에는 다음 중 하나만 내보낸다.

- 좌석만으로 계산한 보수적 하한
- 범위가 넓다는 경고
- 추천 보류

## 4. 이동 가능성을 같은 시나리오에서 계산하기

### 현재 휴리스틱

화면은 같은 30분 구간의 과거 관측이 10회 이상이고 선택한 정류장의 만석 관측 비율이 50% 이상이면 상류 후보를 찾는다. 같은 방향에서 승차할 수 있는 정류장 가운데 관측이 10회 이상이고 만석 비율이 25% 미만인 가장 가까운 지점을 고른다. 현재 오는 버스의 판정이 `여유`나 `빠듯`이면 그 판정을 우선하고, `어려움`일 때는 후보 정류장 이름과 함께 `가세요`라고 표시할 수 있다.

화면이 `탑승 확률`이라고 부르는 값은 `1 - 과거 만석 관측 비율`이다. 줄에서 사용자의 위치나 하차 인원, 후보까지 걷는 시간을 포함한 개인 성공 확률은 아니다.

### 목표 방식

상류 정류장의 좌석이 많아도 사용자가 버스보다 늦게 도착하면 후보가 아니다. 필요한 값은 정류장 개수가 아니라 실제 시간이다.

- 사용자의 출발 위치에서 후보 정류장까지 걸리는 시간
- 버스가 현재 위치에서 후보 정류장까지 오는 시간
- 신호, 횡단보도, 환승 통로에서 생기는 변동

사용자 이동시간을 `T_user`, 버스 도착시간을 `T_bus`라고 하면 먼저 볼 사건은 다음과 같다.

```text
T_user + 안전 여유 < T_bus
```

좌석, 대기열, 이동시간을 후보별로 따로 독립 추정하면 같은 비 오는 날 모든 값이 함께 나빠지는 상관을 놓친다. 목표 모델은 같은 날씨와 혼잡도, 배차 간격을 공유하는 시나리오 안에서 후보 전체를 함께 계산한다.

## 5. 확률보다 행동 비용으로 추천하기

현재 휴리스틱은 조건을 만족하면 강한 이동 문구를 낸다. 아래 내용은 그 출력을 이동 비용과 실패 비용을 함께 따지는 방식으로 바꾸기 위한 목표 설계다.

탑승 확률이 1% 높아졌다고 15분을 더 걷게 해서는 안 된다. 반대로 지각 비용이 큰 날에는 작은 확률 차이도 중요할 수 있다.

행동 `a`의 손실을 다음처럼 둔다.

```text
L(a) = w_move × 이동시간
     + w_wait × 추가 대기
     + w_fail × 탑승 실패
     + w_late × 지각
```

후보 정류장의 손실이 현재 정류장보다 충분히 낮을 가능성이 클 때만 이동을 권한다.

```text
P(L(후보) + 여유폭 < L(현재)) ≥ 신뢰 기준
```

사용자의 비용 가중치를 알 수 없으면 강한 추천 대신 비교 정보를 보여 준다. “여기로 가면 무조건 탄다”가 아니라 “도착 가능성은 높지만 12분을 더 걸어야 한다”처럼 판단 재료를 분리한다.

## 6. 후보 사이의 관계

상류로 갈수록 버스 좌석은 대체로 많아지지만 사용자가 도착하기는 어려워진다. 후보들은 독립이 아니다.

- 같은 버스의 좌석 상태를 공유한다.
- 같은 날의 혼잡 효과를 공유한다.
- 한 후보를 선택하면 다른 후보의 실제 결과는 관측할 수 없다.

따라서 각 후보에 별도 난수를 뽑아 성공 확률을 만든 뒤 가장 큰 값을 고르는 방식은 피한다. 한 시나리오에서 차량과 사용자의 움직임을 같이 생성하고 후보들의 손실을 함께 비교한다.

## 7. 검증 계획

### 수식과 구현

정답을 아는 합성 자료로 다음 상황을 만든다.

- 비만석 단일 전이
- 만석 뒤 계속 만석
- 중간 만석 뒤 하차로 좌석 회복
- API 관측 누락과 지연
- 배차 간격 급증
- 사용자가 후보 정류장에 늦게 도착하는 경우

숨은 상태와 정답을 알고 만든 자료에서도 복원하지 못하면 실데이터 결과가 그럴듯해 보여도 채택하지 않는다.

### 날짜 순서 평가

과거 날짜로 학습하고 다음 날짜를 시험한다. 같은 날 자료를 학습과 시험에 섞지 않는다.

### 층별 지표

| 층 | 지표 |
|---|---|
| 좌석 | 도착 좌석 MAE, 만석 Brier, 예측구간 포함률 |
| 경쟁 수요 | `H` 오차, 실제 탑승 Brier, 확률 구간별 보정 |
| 이동 | 사용자와 버스 ETA 절대오차, 제시간 도착 사건의 보정 |
| 추천 | 실제 선택의 실패 비용, 현재 행동 대비 개선, 추천 보류율 |

선택하지 않은 정류장에서 탔을지를 API 스냅샷으로 정답 처리하지 않는다. 정책 우월성을 비교하려면 안전한 후보 사이의 제한적 무작위화, 선택확률 기록, 또는 여러 정류장의 동시 현장 관측이 필요하다.

## 8. 구현 순서

1. 현재 좌석 예보의 예측구간 보정을 개선한다.
2. 검열 표본을 하한과 상한으로 사용하는 상태 추론을 합성 자료에서 검증한다.
3. 후보 정류장별 `Q`, `A`, 실제 결과를 수집한다.
4. 이동시간과 버스 ETA의 오차 분포를 측정한다.
5. 같은 시나리오에서 좌석, 경쟁 수요, 이동을 결합한다.
6. 기대손실 기반 추천을 제한된 사용자에게 검증한다.

각 단계가 단순 기준선보다 안정적으로 낫지 않으면 다음 단계로 복잡도를 늘리지 않는다.

## 9. 남는 위험

- 행사, 사고, 우회 운행은 학습 범위를 벗어날 수 있다.
- 사용자는 위험한 날에만 앱을 열 가능성이 커 수집 자료가 편향될 수 있다.
- 추천이 사용자의 행동을 바꾸면 이후 학습 자료도 추천 정책의 영향을 받는다.
- 정류장 줄이 선착순이 아니면 `Q`만으로 개인 순서를 설명할 수 없다.
- 직접 기록 부담을 감수하지 않으면 개인 탑승 성공 확률까지 갈 수 없다.

이 위험을 감추기보다, 자료가 부족한 상황에서 추천을 보류하는 것을 정상 출력으로 취급한다.
