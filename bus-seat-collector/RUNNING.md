# 수집 운영 기록

## 데이터 경계

- 공개 `bus-seat-tracker`: 수집기 코드와 워크플로만 보관한다.
- 비공개 `bus-seat-tracker-data`: `data/routes`, `data/snapshots`만 보관한다. 당일 수집은 `collect/YYYY-MM-DD` 브랜치에 누적하고, 다음 날 첫 수집에서 날짜당 한 커밋으로 `main`에 반영한다.
- 공개 화면에는 차량 번호, HMAC 차량 ID, 원본 스냅샷을 전달하지 않는다.

## 시작 전 설정

GitHub Actions Secrets에 다음 값을 등록한다.

| 이름 | 역할 |
|---|---|
| `GYEONGGI_BUS_API_KEY` | 공공데이터포털 일반 인증키 |
| `VEHICLE_HASH_SECRET` | 차량 식별자 가명화를 위한 고정 비밀값 |
| `BUS_DATA_REPO_TOKEN` | `bus-seat-tracker-data`에만 Contents 읽기·쓰기가 가능한 fine-grained PAT |

`VEHICLE_HASH_SECRET`은 API 키와 별개로 유지한다. API 키를 재발급해도 같은 차량의 가명 ID가 유지되고, API 키 유출이 과거 가명 ID 대조로 이어지는 일을 막는다.

## 가동 절차

1. `main`에 `collect-bus-seats.yml`을 반영한다.
2. Actions에서 **Collect bus seats**를 수동 실행한다.
3. 비공개 저장소의 당일 `collect/YYYY-MM-DD` 브랜치 `data/snapshots`에 3330·1650 JSONL이 생겼는지 확인한다.
4. 화면에는 관측 시각을 항상 표시한다.

## 수집 스케줄 (2026-07-23 통근 집중 개편)

### 스로틀링 실측이 구조의 근거다

`cron: '*/5'`로 24시간 돌린 실측(2026-07-19~20): 실제 스케줄 실행 간격 **56~105분**, 최대
**4시간 공백**. GitHub은 고빈도 스케줄을 크게 지연시키므로, 크론 간격을 좁혀도 해상도가
확보되지 않는다. 결론 — **크론은 시동 장치로만 쓰고, 해상도는 잡 내부 루프가 담당한다.**

### 창 배치는 만석 분포 실측이 근거다 (2026-07-23)

평일 3일치 관측에서 만석은 통근 창에 집중된다: 06:30 버킷에서 시작(6.0%)해 07:00~08:00에
절정(14.6~17.9%), 저녁은 17:30 시작(8.3%), 18:00~18:30 절정(16.0~18.1%). 21:00 이후는
0.4% → 0으로 사실상 소멸한다. 따라서 통근 창만 집중 수집하고 심야는 수집을 멈춘다.
주말은 피크 없이 균등 스냅샷으로 전환한다 (기존 주말 저녁 루프 폐지).

### 시간대 티어 (KST)

| 시간대 | 창 | 간격 | 방식 |
|---|---|---|---|
| 평일 아침 피크 | 06:30~10:00 | 10분 | 잡 하나가 창 끝까지 루프 |
| └ 조밀 구간 | 07:00~09:00 | **1분** | 같은 루프가 간격만 바꾼다 |
| 평일 저녁 피크 | 17:30~20:30 | 10분 | 〃 |
| └ 조밀 구간 | 18:00~19:30 | **1분** | 〃 |
| 평일 그 외 | 05:00~21:00 정시 | 1시간 | 매시 크론 1회 스냅샷 |
| 주말 | 06:00~23:00 정시 | 1시간 | 매시 크론 1회 스냅샷 (균등) |
| 심야 | 위 시간대 밖 | — | 수집 없음. 매시 실행은 수집 단계에서 즉시 종료 |

- 시동 크론(UTC): `30 21 * * 0-4`(평일 아침), `30 8 * * 1-5`(평일 저녁), `0 * * * *`(매시 기본)
- **매시 크론이 백업 시동을 겸한다**: 창 시작 60분 전 이후에 도착한 어떤 실행이든 남은 창을
  루프로 이어받는다. 시동 크론이 통째로 스킵돼도 다음 매시 실행이 창을 복구한다.
- 마지막 정시(평일 21시, 주말 23시) 실행이 스로틀로 밀려도 스냅샷을 남기도록 운행 시간대
  판정에 한 시간 여유를 둔다.
- 심야 실행도 잡 자체는 돌므로 전날 브랜치의 `main` 아카이브(자정 이후 첫 실행)는 그대로 동작한다.
- 러너 6시간 한도 보호로 루프는 최대 320분에서 끊고, 잔여 창은 대기 중인 다음 실행이 이어받는다.
- 업로드는 사이클마다 **변경된 파일만** 커밋한다 (체크아웃 시점 파일은 기준선으로 제외).

### 조밀 구간 (2026-07-26 추가)

10분 간격에서는 버스가 관측 사이에 5~7정류장을 지나므로 정류장 단위 승차량을 읽을 수 없다.
대기 인원 복원(`docs/queue-recovery.md`)은 정류장별 도착·출발 잔여석을 각각 잡아야 성립하는데,
현재 해상도에서는 판교역 저녁 통과 차량 중 승차량을 직접 산출할 수 있는 비율이 44%에 그친다.

배치 근거는 위 만석 분포와 필드 기록 시각 두 가지다. 아침 절정 07:00~08:00과 범계역
기록(08:37), 저녁 절정 18:00~18:30과 판교역 기록(18:57)이 모두 조밀 구간 안에 들어온다.

전 피크를 1분으로 돌리면 API가 한도에 육박해 재시도 한 번에 수집이 죽는다. 그래서 창 안의
핵심 시간대에만 적용한다. 주말은 피크 창 자체가 없으므로 해당 없음이다. 간격 판정은 사이클마다
다시 하므로 루프가 구간을 넘나들어도 된다.

### 비용·쿼터 (설계값)

- API: `npm run budget`이 `schedule.ts`의 창 정의에서 직접 센다. 숫자는 `DEPLOY.md` §6에 있다.
  - 조밀 구간 도입 전은 ~100콜/일(10%)이었다. 전 피크를 1분으로 돌리면 한도에 육박해 쓸 수 없다.
  - 창이나 조밀 구간을 넓히기 전에 그 명령을 돌린다. 한도를 넘으면 종료 코드 1로 끝난다.
- 러너: 평일 루프 합계 ~6.5시간/일. 공개 저장소라 무료이며, 수집은 이 프로젝트의 목적 자체다.

### 이벤트 모드

콘서트·경기 날에는 Actions에서 **Run workflow**로 `event-duration-minutes`(예: 240),
`event-interval-seconds`(기본 300)를 입력해 수동 시동한다. 시간대 규칙을 무시하고 즉시
지정 시간 동안 지정 간격으로 수집한다.

### 화면 신선도 기준

`prototype-bus/app.ts`의 `expectedIntervalMinutes()`가 위 창 정의와 같은 값을 갖는다.
정상 ≤ 기대주기×2, 경고 ≤ ×4, 초과 시 중단 배너. 심야 휴지와 운행 재개 직후 2시간은
마지막 정시 스냅샷 이후 경과를 기대 주기로 삼아, 밤새 그리고 새벽 첫 스냅샷이 착지하기
전에 배너가 오작동하지 않게 한다. 창 정의를 바꾸면 두 곳을 같이 바꾼다.

**조밀 구간은 여기에 반영하지 않는다.** 화면 신선도의 하한은 수집 간격이 아니라 Pages 발행
주기(30분, `publish-pages.yml`의 `17,47 * * * *`)다. 기대 주기를 1분으로 낮추면 정상 판정
기준이 2분이 되어 상시 경고 배너가 뜬다. 창 경계는 그대로이므로 앱의 창 정의는 손대지 않았다.

## 자동 검증 (2026-07-26 추가)

`verify-forecast.yml`이 매일 KST 04:00에 층-1 좌석 예보를 스스로 채점한다. 전날 수집분이
`main`에 아카이브된 뒤에 돌도록 시각을 잡았다.

- rolling-origin 백테스트는 테스트일 **이전** 날짜로만 학습하므로, 폴드 하나가 곧 "그날의
  전방 예측이 실제와 얼마나 맞았는가"이고 폴드 배열이 정확도 추이가 된다. 정답은 데이터가
  스스로 주므로(self-supervised) 별도 라벨링이 없다.
- `npm run backtest -- --json=<경로>`가 기계 판독 성적표를 남긴다. 워크플로는 이를
  아티팩트(90일 보관)로 올리고 Actions Step Summary에 표로 푼다.
- **회귀 가드**: 최신 폴드에서 배포 조합의 MAE 또는 Brier가 기준선(`naive-persist`, "좌석
  그대로") 이상이면 잡을 실패시킨다. 예측이 "아무것도 안 하기"보다 못해지면 즉시 드러난다.
- 예측구간 포함률이 60% 밑으로 떨어지면 경고만 낸다(목표 80%).

성적표에는 모든 후보 조합을 함께 싣고 `shippedModel`로 배포 중인 것을 표시한다.
2026-07-26부터 배포 조합은 `deconv-arrival`(구간합 역산 + 도착 귀속)이다. 바꿀 때는
`build-data.ts`의 프로파일 산출과 `backtest.ts`의 `shippedModel`을 같이 바꾼다.

### 라이브 예측 로그

재현 채점은 과거 데이터로 예측을 **다시 만들어** 채점하므로 "그때 화면이 실제로 뭐라고
말했는가"는 검증하지 못한다. 낡은 프로파일이 배포됐거나 발행이 멈춘 종류의 문제는 잡히지
않는다. 그래서 발행할 때마다 예측을 그대로 남긴다.

- `build-data.ts --predictions=<경로>`가 지금 화면에 나갈 예측을 JSONL로 덧붙인다.
  `app.ts`의 `forecastVehicle`과 같은 규격이다 — 정류장당 2분씩 시간 버킷을 전진시키고,
  도착 평균은 그 정류장 수요를 적용하기 **전** 값이며, 회차점 너머는 세지 않는다.
  `minutesPerStop`을 바꾸면 두 곳을 같이 바꾼다.
- 기록 지평은 1·3·6정류장이다. 백테스트의 horizon 구간(1-2 / 3-5 / 6+)에 하나씩 대응한다.
- **차량 가명 ID가 들어가므로 발행 대상 밖에만 쓴다.** 비공개 저장소의 `predictions`
  전용 브랜치(`predictions/<KST 날짜>.jsonl`)에 쌓인다. `publish-pages.yml`만 이 브랜치에
  쓰고 발행 동시성이 1이라 경합이 없다.
- `npm run score`가 다음 날 실제 관측과 대조한다. 예측 시각 이후 그 차량이 대상 정류장에
  잡힌 첫 관측만 인정하고, 샘플링이 대상을 건너뛴 경우는 대조를 포기한다.
- **파이프라인 가드**: 예측이 근거로 삼은 관측이 25분 넘게 낡았으면 잡을 실패시킨다.
  대조율이 2% 밑이면 경고한다.
- 채점이 끝난 기록은 7일 뒤 지운다. 브랜치 이력은 계속 자라므로, 커지면 orphan 커밋으로
  한 번 눌러 주는 것이 맞다.

10분 간격에서는 대상 정류장을 정확히 잡을 확률이 낮아 대조율이 5%를 밑돈다. 조밀 수집
구간에서 크게 오를 값이며, 이 지표 자체가 수집 해상도의 척도다.

### 이 채점이 보지 못하는 것

구간합 지표만 본다. 정류장 단위 수요 배분 차이(검증 보고서 §4·§7)와 만석 검열로 가려진
초과 수요(`docs/queue-recovery.md` §1)는 여기에 나타나지 않는다. 두 모델이 구간합에서
동급으로 보여도 정류장 단위에서는 갈릴 수 있다.

## 보관 원칙

원본 JSONL은 비공개 저장소에만 둔다. 공개 배포를 시작할 때는 차량 식별자를 제거한 정류장·시간대 집계만 별도 API로 제공한다.
